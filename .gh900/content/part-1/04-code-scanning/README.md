## Unit 1 — Introduction

Official unit: <https://learn.microsoft.com/en-us/training/modules/configure-code-scanning/1-introduction>

Code scanning is static-analysis functionality integrated into GitHub's security experience. It analyzes repository code and reports potential vulnerabilities or coding errors as code-scanning alerts.

For public repositories, GitHub code scanning is available broadly. Private-repository availability depends on organization/enterprise security licensing and configuration.

## Unit 2 — What is code scanning?

Official unit: <https://learn.microsoft.com/en-us/training/modules/configure-code-scanning/2-what-code-scanning>

### Purpose

Code scanning helps teams:

- identify existing security weaknesses and coding errors;
- prioritize and triage findings;
- catch new problems during development;
- surface findings in the repository Security experience and pull-request checks;
- close findings when the vulnerable/error-producing code is fixed.

### CodeQL

CodeQL is GitHub's semantic code-analysis engine. It treats source code as queryable data:

1. create a CodeQL database representing the codebase;
2. execute security/correctness queries;
3. produce findings;
4. upload/display results as GitHub code-scanning alerts.

The Microsoft Learn unit lists support for major languages including C/C++, C#, Go, Java/Kotlin, JavaScript/TypeScript, Python, Ruby, and Swift. Supported-language details can evolve, so live documentation is the authoritative compatibility reference.

### Three primary CodeQL setup approaches

#### Default setup

GitHub chooses much of the configuration automatically, such as supported languages, query suites, and common events. It is the fastest way to enable CodeQL and runs through GitHub Actions.

Use default setup when the repository is conventional and does not require custom build or workflow logic.

#### Advanced setup

GitHub creates a CodeQL workflow file under `.github/workflows/`. You control the workflow and can customize:

- triggers;
- languages;
- query suites;
- build steps;
- scan frequency;
- other workflow behavior.

Use advanced setup when the repository needs non-default build commands, special scheduling, custom queries, or other workflow-level control.

#### External CI / CodeQL CLI

Analysis can run outside GitHub Actions using the CodeQL CLI or another supported tool/CI platform. Results are then uploaded to GitHub so alerts appear in the normal code-scanning UI.

### Alert lifecycle

A finding normally appears in **Security → Code scanning** and can also surface in relevant PR checks. Alerts can include rule information, location/data flow, severity/security severity, affected branch/analysis, and remediation context.

Once code is fixed and a subsequent analysis no longer reports the finding, GitHub can close the alert. Authorized users can also dismiss alerts with an appropriate reason when justified.

## Unit 3 — Enable code scanning with third-party tools

Official unit: <https://learn.microsoft.com/en-us/training/modules/configure-code-scanning/3-enable-code-scanning-with-third-party-tools>

### SARIF

GitHub can ingest static-analysis results generated by external tools using **SARIF (Static Analysis Results Interchange Format)**.

The curriculum focuses on SARIF **2.1.0**.

A supported scanner can:

1. analyze code in an external CI system or local automation;
2. produce SARIF;
3. upload SARIF to GitHub;
4. have GitHub turn the results into code-scanning alerts.

### Upload mechanisms

Common mechanisms include:

- the code-scanning REST API;
- CodeQL CLI upload functionality;
- GitHub Actions, including SARIF upload actions.

The correct method depends on where/how the analysis ran.

### Code-scanning API concepts

The API can be used to work with items such as:

- alerts;
- analyses;
- CodeQL databases;
- default-setup configuration;
- SARIF uploads.

This enables enterprise reporting and external CI integration.

Do not confuse **uploading SARIF** with executing CodeQL itself. SARIF is an interchange/result format; the analysis may have been generated by CodeQL or a third-party scanner.

### Third-party integration model

A third-party scanner does not need to reproduce GitHub's UI. It runs analysis and uploads normalized results; GitHub provides a common alert/review experience.

## Unit 4 — Configure code scanning

Official unit: <https://learn.microsoft.com/en-us/training/modules/configure-code-scanning/4-configure-code-scanning>

### Workflow location

Advanced GitHub Actions workflows are stored under:

```text
.github/workflows/
```

A CodeQL workflow is commonly named something such as `codeql.yml` or `codeql-analysis.yml`.

### Default → advanced

A repository using default setup can be switched to advanced setup when greater control is required. The important exam concept is that **default setup is managed/low-configuration**, while **advanced setup is workflow-defined/customizable**.

### Triggering analysis

Common trigger models include:

#### Push

Scanning on `push` analyzes code when changes reach configured branches. This is useful for continuously evaluating the default/protected branches.

#### Pull request

Scanning on `pull_request` provides security feedback before a change is merged. Findings attributable to the PR can appear in PR checks/security feedback.

#### Schedule

Scheduled scans are useful even when code does not change because query packs/security knowledge can improve over time and newly recognized vulnerabilities can be detected in unchanged source.

Example conceptual workflow trigger:

```yaml
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
  schedule:
    - cron: '30 5 * * 1'
```

The exact schedule should reflect repository risk and workflow cost, not an arbitrary certification value.

### Language/build configuration

Compiled projects may require build logic so CodeQL can observe a valid build. Advanced setup can be necessary when automatic build detection is insufficient.

Configuration can also control which languages or directories are analyzed and which queries are executed.

### Frequency tradeoff

Event-driven scans provide immediate feedback around changes. Scheduled scans provide periodic reassessment. Mature repositories often combine them.
