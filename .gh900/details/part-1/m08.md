# Source-audited additions — Module 8

## m08-u02

Markdown deliberately sits between plain text and HTML: it keeps source readable while adding enough structure for headings, emphasis, links, code, lists, tables, and other common documentation patterns. GitHub renders **GitHub-Flavored Markdown (GFM)**, which adds GitHub-specific conveniences on top of basic Markdown.

Text emphasis can be expressed with `*italic*`/`_italic_` and `**bold**`/`__bold__`; styles can be nested when delimiters are paired consistently. A backslash escapes Markdown punctuation when the character should be shown literally. Headings use one through six `#` characters. Links use `[text](target)`, while images prefix that pattern with `!` and should include useful alt text.

Ordered lists use numeric markers and unordered lists can use `-` or `*`; indentation creates nested levels. Tables use pipe-separated cells and a dash row to identify the header. `>` creates a blockquote. Markdown can also contain inline HTML for formatting cases Markdown itself does not express, although repository/community conventions should determine when that is appropriate.

For code, a single backtick marks **inline code**. Triple-backtick fences create multi-line code blocks; adding a language identifier such as `javascript`, `python`, or `yaml` enables syntax highlighting. Code fences are preferable to trying to format program text as ordinary paragraphs because whitespace and symbols are preserved predictably.

GFM can automatically cross-link repository activity. A local issue or pull request can be referenced with `#NUMBER`; GitHub also recognizes full issue/PR URLs and qualified references such as `owner/repository#NUMBER`. Pasting a commit URL or a sufficiently long commit SHA creates a link to that commit; qualified repository/SHA forms can disambiguate references from another repository.

An `@username` or valid `@organization/team` mention can notify and link the person/team, subject to visibility/notification rules. Mentions should be used intentionally rather than as a substitute for appropriate assignment or review requests.

Task lists use checkboxes such as `- [ ]` and `- [x]` and are useful in issue/PR descriptions for visible progress. GitHub also offers **slash commands** in supported issue, pull-request, or discussion editing surfaces. The pinned lesson calls out commands for inserting code blocks, collapsible details, saved replies, tables, task lists, and repository templates. Slash commands are editor productivity features; the produced content is still Markdown/GFM.

The important GitHub-specific skill is understanding how Markdown participates in collaboration: references connect conversations to issues/PRs/commits, mentions bring people into a thread, task lists expose progress, and formatted code/tables make technical discussion reviewable. Good Markdown is not decorative—it makes repository knowledge easier to scan and connect.

## m08-u05

After the module, you should be comfortable reading and writing the Markdown constructs GitHub uses every day: emphasis, headings, links/images, ordered/unordered and nested lists, tables, blockquotes, inline/fenced code, and occasional inline HTML. You should also recognize the GFM collaboration extensions: autolinked issue/PR/commit references, mentions, task lists, syntax-highlighted fences, and supported slash-command helpers.

For practical work, prefer clear structure over clever formatting: descriptive link text and image alt text, meaningful headings, fenced code with the right language, tables only when tabular comparison helps, and references that preserve traceability to the GitHub object being discussed.
