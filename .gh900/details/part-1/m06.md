# Source-audited additions — Module 6

## m06-u02

A Codespace has a lifecycle from **creation to deletion**, and several actions in the middle have very different consequences. Disconnecting from an active Codespace does not stop its processes. Stopping it ends active compute but preserves the environment's stored work. Restarting resumes that stopped environment. Rebuilding reconstructs the dev container. Deleting removes the Codespace itself, so unpushed work can be lost.

A Codespace can be created from several contexts: a GitHub/template repository for a new project, a repository branch for feature work, an open pull request to investigate work in progress, or even a historical commit when diagnosing behavior at a specific point. A developer may create a fresh Codespace for short tasks or retain a long-running one. With long-running environments, regularly pull the default branch; with disposable/new environments, push committed changes frequently so the remote repository remains the durable record.

The creation sequence includes provisioning a virtual machine and storage, creating the containerized development environment, establishing the editor connection, and running post-create setup. **Prebuilds** can be configured by repository administrators to perform expensive setup ahead of time and make environment startup faster.

Changes made in the Codespace are stored on its cloud VM, but that is not equivalent to pushing them to GitHub. Web-based VS Code normally enables AutoSave; desktop VS Code may require the user to enable it. Saved-but-uncommitted changes can survive a normal stop/restart, but deleting the Codespace removes the environment. Commit and push anything that must become durable team history.

Codespaces can be reopened through GitHub.com, VS Code, supported JetBrains tooling, or GitHub CLI. An inactive running Codespace eventually times out and stops; the pinned Microsoft source gives a default **30-minute inactivity timeout**, while personal configuration can change the default and organization policy can override it. Codespaces also require an internet connection to access the remote environment; if connectivity drops, the environment retains state, but the client cannot interact with it until connectivity returns.

Billing behavior also follows lifecycle state: running Codespaces consume compute, whereas stopped Codespaces primarily retain storage. Stopping an idle environment therefore matters for cost. A stop/restart is also needed for some changes such as a machine-type change.

A **rebuild** applies dev-container configuration changes. During container rebuild, content under `/workspaces`—including the repository clone—is preserved, while changes made elsewhere in the container may be cleared. A full rebuild can discard cached images/setup state as well. When a task is finished and all desired changes are pushed, the Codespace can be deleted. GitHub warns about unpushed commits and can offer recovery/export choices in relevant flows.

Stopped/inactive Codespaces are eventually automatically deleted according to retention settings. The pinned lesson describes a default inactive retention window of **30 days**, with configurable retention within supported limits. The exam distinction is therefore: **stop** to preserve the environment without running compute, **rebuild** to reconstruct configuration while preserving workspace content, and **delete** when the environment is no longer needed after durable work has been pushed.

## m06-u03

Codespaces has two customization layers that should not be confused. A repository's **dev container configuration** describes the repeatable project environment shared by contributors. Personal settings such as dotfiles and editor synchronization customize an individual developer's experience across Codespaces.

Personalization options in the pinned curriculum include:

- **VS Code Settings Sync** for settings, extensions, themes, and keyboard shortcuts across local/web Codespaces experiences;
- a **dotfiles repository** for shell configuration, scripts, aliases, and other personal environment setup;
- renaming the generated Codespace display name to distinguish multiple environments;
- selecting/changing a shell or installing a preferred shell, including configuring it through dotfiles;
- changing the **machine type** to match CPU/memory requirements;
- selecting a default editor such as VS Code desktop, VS Code web, supported JetBrains Gateway environments, or JupyterLab where offered;
- selecting a default region for where the Codespace is hosted;
- changing the inactivity timeout, subject to organization policy;
- configuring automatic deletion/retention for stopped Codespaces within supported limits.

Extensions/plugins can also be installed. VS Code extensions come from the VS Code Marketplace and may run in the local UI or remote Codespaces extension host depending on extension design. JetBrains-based Codespaces can use JetBrains plugins. Settings Sync is useful when the goal is to reproduce personal editor preferences; a dev container is the correct mechanism when the goal is to ensure every contributor receives the project's required tools/runtime/dependencies.

A practical rule is: **project requirements belong in version-controlled dev-container configuration; personal preferences belong in user-level customization**. This preserves reproducibility without forcing one person's theme, aliases, or keyboard shortcuts on the entire team.

## m06-u07

By the end of Codespaces, you should be able to distinguish the environment itself from its configuration and from lightweight browser editing. A Codespace is a remote compute environment with storage, container setup, terminals, extensions, and a lifecycle that can incur compute/storage cost. A dev container makes that environment reproducible for a repository. Personal settings/dotfiles refine the developer experience without redefining project requirements.

Also distinguish **github.dev** from Codespaces: github.dev is a lightweight browser-based editor over repository content and does not provision the full remote VM/container development environment. Choose Codespaces when code must run/build/debug with a controlled toolchain; choose github.dev when the task is primarily a quick repository edit or inspection that does not need that compute environment.
