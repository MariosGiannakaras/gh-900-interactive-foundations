# Source-audited additions — Module 4

## m04-u01

Code scanning is part of GitHub's code-security workflow: it analyzes source code for vulnerabilities and coding errors and turns supported findings into repository alerts developers can triage in the same place they review code. The important architectural point is that analysis does not have to be performed by one specific engine or even inside GitHub. CodeQL can run through GitHub's setups, while supported third-party/static-analysis tools can produce results elsewhere and upload them into GitHub's code-scanning alert model.

This module therefore covers three related decisions: **how analysis is configured**, **where analysis runs**, and **how results are delivered/triaged**. Default setup optimizes for fast GitHub-managed enablement; advanced setup provides a workflow you can customize; external/third-party analysis commonly integrates through SARIF uploads or the code-scanning API.

## m04-u03

Third-party tools can run static analysis outside GitHub and still surface findings as normal GitHub code-scanning alerts. The interchange format used by this workflow is **SARIF (Static Analysis Results Interchange Format)**; the pinned Microsoft unit requires **SARIF 2.1.0** for uploaded results.

### Ways to upload analysis

Choose the upload route based on where/how the analysis was generated:

- **Code-scanning REST API** — useful for automation/reporting systems or scanners that operate outside GitHub Actions. The API exposes code-scanning alerts, analyses, databases, and setup information, and supports uploading externally generated analyses.
- **CodeQL CLI** — a standalone analysis tool that creates a CodeQL database representing the codebase, runs queries/query suites against that database, produces SARIF, and can upload results. The Microsoft unit recommends using the **CodeQL bundle**, because it packages a compatible CLI, queries/libraries, and precompiled queries together; this avoids version mismatch and improves performance compared with assembling those components separately.
- **GitHub Actions** — a workflow can run a scanner and then invoke `github/codeql-action/upload-sarif` to upload a SARIF file or directory.

The code-scanning API is accessed through GitHub's HTTPS API and normally exchanges JSON. For retrieving an analysis in SARIF form, the unit calls out the custom media type **`application/sarif+json`** on the analyses endpoint; SARIF responses can contain GitHub-added metadata such as alert numbers/URLs in addition to the uploaded analysis information.

### `upload-sarif` workflow concepts

A workflow that uploads third-party output lives under `.github/workflows`. The core input is the path in **`sarif-file`** (file or directory, relative to the repository/workspace context). Other configuration concepts documented by the source include the checkout/source path used to relativize absolute locations, the GitHub token, matrix/category metadata for distinguishing analyses, and an option to wait for processing.

The upload step can be part of a scanner workflow or a separate workflow that uploads a SARIF artifact produced elsewhere. Typical triggers include `push` and a scheduled run. A CI system can run its own static analyzer (for example, a linter that supports a SARIF formatter) and then upload the resulting file after the analysis step.

### Avoiding duplicate alerts

SARIF results can contain **`partialFingerprints`**. GitHub uses fingerprints to correlate the same underlying finding across repeated analyses so a recurring issue does not appear as an unrelated new alert every run. CodeQL-produced SARIF contains fingerprint information. If an uploaded SARIF file lacks it, the `upload-sarif` action can attempt to derive fingerprints when it has the source code and SARIF context available.

### Upload limits in the pinned curriculum

The pinned Microsoft lesson states two practical upload limits that are worth recognizing:

- up to **5,000 results per SARIF upload**; excess results are ignored;
- up to **10 MB gzip-compressed SARIF per upload**; oversized uploads are rejected.

If a tool exceeds those constraints, the preferred response is not to split meaningless noise indefinitely but to configure the scanner/rules so the uploaded analysis focuses on relevant findings.

The architecture to remember is: **analyzer → SARIF 2.1.0 → upload/API → GitHub processing → code-scanning alerts**. This lets teams keep an existing CI/security scanner while still using GitHub's alert triage and pull-request integration.

## m04-u04

Advanced code-scanning configuration exists for repositories that need more control than default setup. Enabling **advanced setup** generates a customizable workflow. Many repositories can use the generated workflow with few or no edits, but teams can change scan events/frequency, languages, directories/path scope, query configuration, and build commands when the codebase requires a special compilation process.

If a repository already uses default CodeQL setup, the source describes switching through the repository's Advanced Security/code-scanning settings: switch to advanced, disable the current CodeQL default configuration as prompted, and re-enable scanning through the generated advanced workflow. Workflow files live in `.github/workflows`; a conventional filename is `codeql-analysis.yml`.

### Trigger strategy

**Push scanning:** CodeQL workflows can scan pushes to the default branch and protected branches. The workflow must exist on a branch for that branch's configured event to trigger it. Push results are visible in repository security results and may also map to an open PR when GitHub can associate the analyzed branch with that PR.

**Pull-request scanning:** the `pull_request` event provides security feedback as a PR check before changes land. The Microsoft unit notes the special policy around private-fork PR workflows: whether those workflows run depends on repository settings. For accuracy/efficiency, a PR scan can analyze the PR's merge commit (the candidate result of merging into the base) rather than treating the branch head alone as the final integration state. If an external CI system cannot trigger directly on PRs, push-based scanning can still be associated with open pull requests where GitHub can map the analysis.

**Scheduled scanning:** event-based scans catch changes introduced by developers; scheduled scans can discover newly recognized vulnerabilities even when nobody has recently changed the repository. The default advanced CodeQL example also has a periodic schedule. The pinned unit describes the default weekly schedule and shows changing the `cron` expression when teams need a specific cadence.

### Narrowing unnecessary scans

Workflow filters can avoid running expensive analysis when irrelevant paths change. For example, `pull_request.paths-ignore` can exclude documentation-only changes such as `**/*.md` and `**/*.txt`, while `paths` can positively select files that should trigger scanning. The design tradeoff is to reduce noise/cost without accidentally excluding paths that can affect the executable/security behavior.

### Pull-request failure severity

A code-scanning alert and a failed PR check are related but not identical concepts. The pinned unit says that, by default, severity **Error** or security severity **Critical/High** causes a code-scanning PR check failure. Organizations can configure the failure threshold. Repository settings can do this, while **rulesets** are presented as the more modern/preferred governance mechanism where applicable. A failing security check can prevent merge when the branch/ruleset requires that check.

### Alert triage and dismissal

Fixing the vulnerable code is the preferred resolution. Some findings, however, may be confirmed false positives, test-only conditions, or accepted risks. A dismissal should therefore be a reviewed security decision, not a way to obtain a green check. GitHub records the dismissal reason, closes/removes the alert from the current open-alert view, and uses the dismissal when matching the same code/finding in later scans. Dismissal applies across branches for that alert context.

Add a clear dismissal comment when appropriate: why the code does not need a fix, who reviewed it, whether the decision is temporary/permanent, and any compensating control/follow-up. Organizations can use **delegated alert dismissal** to restrict who may close findings, which creates stronger separation of duties and auditability.

### Copilot Autofix

Copilot Autofix can propose targeted changes for supported code-scanning alerts. The pinned Microsoft unit explicitly treats these as **suggestions**, not automatic trusted fixes. A reviewer should understand the alert, inspect the proposed diff, confirm intended behavior is preserved, run application/security tests, modify the suggestion if necessary, commit it through the normal PR workflow, and confirm the alert is resolved after scanning again. The source also notes that using Autofix in supported code-security contexts does not necessarily require a separate general Copilot subscription.

The configuration principle is to tune scanning so developers receive relevant, timely feedback while keeping the security record auditable: choose triggers deliberately, keep the workflow aligned with the build, use severity/rulesets consciously, and treat dismissal/autofix as reviewed security actions.

## m04-u07

After this module you should be able to explain more than "CodeQL scans code." You should recognize the available setup patterns (default, advanced, external/third-party), know why SARIF allows non-GitHub scanners to feed GitHub alerts, choose an appropriate trigger strategy, understand how PR checks and alert severities interact, and triage findings without destroying the audit trail.

You should also be able to identify when customization is justified: special build commands/languages, scanning only relevant paths, a required schedule, a third-party analyzer, organization rules for scan results, or controlled alert dismissal. Security automation should improve developer feedback while preserving review and accountability.
