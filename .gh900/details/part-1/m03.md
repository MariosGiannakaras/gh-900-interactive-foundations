# Source-audited additions — Module 3

Billing, plan, and quota values in this module are tied to the pinned Microsoft Learn source snapshot dated **2026-08-06**. These values can change; for operational purchasing decisions, verify the current GitHub pricing/billing documentation. For GH-900 study, understand both the product distinctions and what the pinned curriculum explicitly teaches.

## m03-u02

GitHub account type and GitHub plan are related but different decisions. A **personal account** represents an individual. An **organization** is a shared namespace and permission boundary for teams and repositories. An **enterprise account** sits above organizations and centralizes governance, identity, policy, licensing, and billing across them. Enterprise deployments can use GitHub Enterprise Cloud, GitHub Enterprise Server, or an enterprise configuration that combines relevant capabilities.

The pinned curriculum distinguishes these plan families:

- **GitHub Free for personal accounts** — core public/private repository collaboration plus community support and platform features appropriate to individuals. The source also calls out Dependabot alerts, account security such as 2FA enforcement, GitHub Packages, an included Codespaces allowance, and an included GitHub Actions allowance.
- **GitHub Pro** — the paid personal plan. It expands support and private-repository collaboration capabilities, including features such as required reviewers/code owners and additional repository insights, Wikis/Pages-related capabilities, and larger included automation/development allowances compared with Free.
- **GitHub Free for organizations** — shared repositories and organization collaboration without the paid Team feature set.
- **GitHub Team** — paid organization collaboration and administrative capabilities intended for professional teams, including stronger repository controls and support.
- **GitHub Enterprise** — centralized enterprise governance, policy, identity, security, and billing. The pinned source describes Enterprise Cloud and Server deployment choices and enterprise-wide controls.

In the pinned curriculum, GitHub Enterprise Cloud includes a substantially larger Actions allowance than lower plans (the source gives **50,000 minutes/month**), enterprise-oriented Packages capacity, centralized policy/billing, and an SLA/support model. Do not infer that every adjacent GitHub product is bundled automatically: the Microsoft unit explicitly notes that **GitHub Copilot is not simply included by default with GitHub Enterprise**; Copilot has its own plans/licensing and policy controls.

**Enterprise Managed Users (EMU)** are an enterprise identity model in which user accounts are provisioned and governed by the enterprise's identity provider instead of being ordinary personal GitHub.com identities that users independently control. EMU is important when a scenario requires centralized lifecycle and identity governance rather than merely SAML authentication of ordinary accounts.

When comparing plans on the exam, reason from the requirement: individual vs shared organization vs enterprise governance, private-repository control depth, support expectations, included consumption allowances, identity requirements, and whether a capability is a separately licensed product.

## m03-u06

**Machine accounts** are GitHub accounts used by automation rather than a human working interactively—for example, scripts or some third-party automation. In the pinned curriculum, a machine account can consume a GitHub license like a normal user account, so stale automation identities create both security and cost concerns. They should be inventoried, given only the permissions they need, and removed or disabled when no longer justified.

The unit separately discusses **peripheral services**: integrations and automation that interact with GitHub through APIs or workflow infrastructure. Examples include CI/CD systems, security scanners, third-party services such as chat/issue-management/observability integrations, and runner infrastructure. The administrative problem is not just "how many people have seats?" but also "which automated identities and services are active, what access do they retain, and what metered resources do they consume?"

The source describes several inspection paths:

- enterprise billing/license views for active machine-account and license information where available;
- GraphQL-based inventory queries that can surface machine-account identity and activity information across organizations;
- Actions/runners usage views for hosted and self-hosted execution;
- REST endpoints for enterprise runner inventory;
- the enterprise **audit log** to investigate API/integration activity.

A useful operating loop is: inventory automation identities and integrations, identify last activity/ownership, remove stale access, reduce excessive permissions, monitor API/rate-limit behavior, and review runner consumption. Idle or forgotten machine accounts are not only wasted licenses; because they often hold credentials or broad repository access, they can become a privilege-escalation or supply-chain risk.

## m03-u07

GitHub uses **metered consumption** for several products, so administrators need to understand both included allowances and actual usage. Consumption reports are used to attribute cost, notice unexpected growth, and decide whether to optimize workflows or remove unused access.

For **GitHub Actions**, the pinned Microsoft source breaks usage down by repository, runner operating system/type, consumed minutes, and remaining allowance. It states that public repositories receive unlimited standard GitHub-hosted Actions minutes and gives these private-repository monthly included allowances for that source snapshot: **Free 2,000 minutes, Pro 3,000, Team 3,000, Enterprise 50,000**. The same source lists then-current example hosted-runner rates of **$0.008/min Linux, $0.016/min Windows, and $0.08/min macOS**. These are time-sensitive billing values, not permanent platform constants. Common cost controls are to avoid redundant jobs, cache dependencies, narrow triggers, and choose runner strategy deliberately.

**GitHub Packages** consumption includes stored package data and data transfer. The curriculum emphasizes deleting unused packages/using retention, avoiding unnecessary duplication, and checking the current pricing documentation when limits matter.

For **GitHub Enterprise licensing**, the unit teaches administrators to compare active users with allocated licenses and to remove inactive access so seats can be managed efficiently. Identity automation such as SSO/SCIM can make lifecycle management more reliable than periodic manual cleanup.

For **GitHub Advanced Security / GitHub security products**, licensing is tied to security-product usage rather than simply repository count. The pinned unit describes an **active committer** concept using a 90-day activity window and counts a unique committer once even if that person contributes to multiple protected repositories. The exact commercial packaging/naming can evolve, so learn the governing idea: security licensing tracks the people actively contributing to repositories where the paid security capability is enabled.

**GitHub Copilot** is another separately managed per-user service. Administrators can review assigned/active users and remove seats that are not needed. Eligibility for no-cost access (for example, qualifying students or verified open-source maintainers) is a separate concept from organization/enterprise paid assignment.

**Git LFS** meters large-file storage/bandwidth independently from normal Git history. The pinned lesson mentions storage/bandwidth allowances and recommends pruning unused LFS objects or moving unsuitable large assets to purpose-built external object storage when appropriate.

The cross-product lesson is that "GitHub bill" is not one counter. Seats, Actions compute, Packages/storage/data transfer, LFS, security products, Copilot, and other metered capabilities have different units of consumption. A good administrator identifies the resource that is actually driving cost before trying to optimize it.
