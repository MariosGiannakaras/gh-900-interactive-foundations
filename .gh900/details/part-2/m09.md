# Source-audited additions — Module 9

## m09-u02

Open source means more than a public repository: the project must grant rights to use, modify, and redistribute the software through an appropriate **open-source license**. A public repository with no license is viewable, but viewers do not automatically receive open-source permissions. Before contributing, inspect the repository's community and legal guidance.

A useful first-pass checklist is:

- **LICENSE** — what rights/obligations govern use and contributions;
- **README** — what the project does and how newcomers get started;
- **CONTRIBUTING** — development setup, contribution process, tests/style/commit conventions, and expectations for PRs;
- **CODE_OF_CONDUCT** — behavioral expectations and community safety.

A project may not have every community file, but clear contribution and conduct guidance is a positive sign that maintainers have thought about onboarding. Also inspect Issues, pull requests, Discussions/forums, and any chat/community links to understand how maintainers actually communicate and whether the project is active.

GitHub search can be used to find repositories/topics related to an area of interest. Starting with software you already use is often easier because you have context for what is confusing, broken, or outdated. Useful first contributions are not limited to code: documentation corrections, broken links, examples, issue triage, design/testing feedback, and reproducible bug reports can all be valuable.

For beginner-friendly work, repository `/contribute` pages and labels such as **`good first issue`**, **`help wanted`**, or project-specific newcomer labels are common discovery mechanisms. Read the issue carefully before volunteering: check assignees, comments, and linked PRs to avoid duplicating work already underway.

GitHub Sponsors represents a different form of contribution. Eligible maintainers/projects can expose a Sponsor button and funding tiers. Financial support, documentation, mentorship, community work, and code are all valid ways to contribute to an open-source ecosystem.

## m09-u03

Communication should happen **before** substantial implementation. On an existing issue, check whether somebody is assigned, whether a pull request is already linked, and whether another commenter has said they are working on it. If the work is free, comment publicly to express intent and allow maintainers to give direction. For a new bug/feature, create an issue using the repository template/form and obtain agreement before investing in a large or potentially controversial change.

The standard external-contributor workflow is fork-based because contributors normally cannot push directly to the upstream repository:

1. **Fork** the upstream repository into an account/organization you control.
2. Clone your fork by HTTPS/SSH/CLI (or use GitHub Desktop/Codespaces).
3. Prefer a dedicated branch for each contribution so unrelated changes remain isolated.
4. Make changes, stage them, and commit with messages that follow the project's conventions.
5. Push the branch to your fork; when first pushing, establish the upstream tracking relationship as needed.
6. Open a pull request from the fork branch to the upstream repository's target branch.

In this workflow, `origin` normally refers to the fork you cloned. Contributors often add the original project as another remote conventionally named `upstream` so they can fetch/synchronize upstream changes. The terms are conventions rather than magic names: what matters is knowing which remote you can push to and which repository is the source project.

A good pull request gives maintainers enough context to review: accurate title, what changed, why it changed, relevant testing, and a reference to the issue (for example `#123`) when appropriate. If the repository provides a PR template, fill it out rather than deleting requested information.

Pull requests contain not only commits/diffs but also conversation, code review, and **status checks**. Automated checks might enforce build/test behavior, formatting, policy, or security. A contribution is normally expected to satisfy required checks; when a check fails, inspect its Details/log output and fix the underlying problem. If the failure is unclear, ask maintainers publicly rather than guessing or attempting to bypass the check.

A **draft pull request** is useful when you want early design/help feedback before claiming the change is ready to merge. Review can result in approval, requested changes, or comments/questions. New commits pushed to the PR branch update the same pull request; you do not open a new PR for each revision.

Open-source review requires patience. Maintainers may be volunteers with other obligations. Follow the project's Code of Conduct, keep discussion public so others can learn and contribute, and avoid private-message escalation solely to obtain faster review. The goal is not merely to get a patch merged but to collaborate within the project's process.

## m09-u05

After a first contribution, deeper participation can happen through issue/PR conversations, repository **Insights → Contributors**, organization/user/enterprise following, project chat/forums, meetups/conferences, newsletters, podcasts, mailing lists, or regular community office hours. The appropriate channel is usually documented by the project rather than chosen by the contributor ad hoc.

Reusable work can sometimes become its own maintained artifact. The Microsoft unit describes several paths: publish functionality as a reusable library/dependency, maintain a fork/mirror for a specialized use case, or package automation as a **GitHub Action**. Actions/apps can be shared through GitHub Marketplace for discoverability where publishing requirements are met.

Those choices create maintenance obligations. A fork must be kept synchronized with upstream to receive important fixes. A reusable library/action attracts users who may report bugs, request features, or depend on compatibility. Before turning a one-off contribution into a public project, consider whether you can document it, triage issues, review external contributions, handle security updates, and set realistic expectations.

If long-term maintenance is not appropriate, a public Gist, technical write-up, or contribution back to the original project can sometimes share the idea without creating another dependency that users expect to be maintained.

## m09-u07

The module's main workflow is: identify a healthy project and its contribution rules, find work that actually needs help, communicate intent before duplicating effort, work in a fork/branch when you lack upstream write access, open a well-contextualized PR, pass project checks, respond respectfully to review, and stay involved through the community channels the maintainers use.

Remember that "contribution" is broader than code. Documentation, issue triage, reproducible reports, reviews, community support, design, mentorship, and sponsorship can all strengthen an open-source project. The legal prerequisite is still the project's license; public visibility alone is not an open-source grant.
