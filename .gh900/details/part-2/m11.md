# Source-audited additions — Module 11

## m11-u02

Repository security begins with a **secure development strategy**, not with enabling one scanner at the end. The pinned Microsoft lesson highlights three recurring challenges: security knowledge must stay current, features/code must be designed and implemented securely, and applications must satisfy relevant policies/regulations throughout their lifecycle. Security education and controls therefore need to be continuous.

A **shift-left** approach moves security feedback earlier into design, coding, pull requests, and CI rather than leaving security as a deployment gate. This does not mean "developers replace security specialists"; it means security checks and feedback become ordinary delivery activities so issues are found when they are cheaper and faster to correct.

The repository **Security** area brings several GitHub controls together:

- a security policy (`SECURITY.md`) describing how vulnerabilities should be reported;
- Dependabot alerts for vulnerable dependencies/malware signals;
- repository security advisories for private coordinated vulnerability discussion/fixing before publication;
- code scanning for code vulnerabilities/errors;
- secret scanning and push protection for leaked credentials/tokens.

For public repositories, the pinned source notes that push protection is enabled by default in applicable GitHub secret-scanning behavior. Regardless of product defaults, the conceptual goal is to detect a secret **before** it becomes durable public history whenever possible.

### `SECURITY.md` and advisories

`SECURITY.md` gives researchers/contributors a safe disclosure path instead of encouraging public issue disclosure of an exploitable vulnerability. A repository security advisory then provides maintainers a private place to coordinate analysis and a fix. Once ready, the advisory can be published; vulnerability identifiers/advisory ecosystems can then help downstream users understand affected versions and upgrade.

### `.gitignore` is prevention, not secret remediation

`.gitignore` tells Git tooling which matching untracked files normally should not be staged. Patterns can match extensions, generated directories, root-only paths, or nested paths; repositories can use more than one `.gitignore`, with directory-local rules affecting that subtree. GitHub also maintains starter `.gitignore` examples for common ecosystems.

But `.gitignore` is not a security boundary and does **not** remove anything already committed. A user can deliberately force-add an ignored file, and a rule can simply miss a sensitive path. If a credential reaches Git history, assume it has been exposed: revoke/rotate the secret first, then follow the supported sensitive-data removal/history-rewrite process when necessary. Merely deleting the file in a later commit does not erase older history or existing clones/caches.

### Branch protection, reviews, and code ownership

Branch protections/rulesets can enforce workflows such as a pull request before merge, required approving reviews, required status checks, or other repository policies. Status checks can build the code, lint it, run tests, or execute security checks. Protection turns those controls from advice into merge requirements.

Required PR review improves accountability on important branches. The pinned unit calls out options such as requiring Code Owner review, dismissing stale approvals when new commits arrive, and requiring approval from somebody other than the last pusher. These controls reduce the chance that a contributor can both change and unilaterally approve sensitive code.

A `CODEOWNERS` file maps paths/patterns to responsible users or teams, for example a JavaScript pattern or a sensitive build directory. GitHub can automatically request those owners for matching PR changes, and branch/ruleset configuration can require their approval. `CODEOWNERS` can be stored in supported locations such as the repository root, `docs`, or `.github`; the repository's rules determine whether an owner request is merely informational or a merge requirement.

### Security is a layered workflow

No single control replaces the others. `.gitignore` reduces accidental local inclusion but does not detect all secrets. Secret scanning detects known credential patterns but does not replace least privilege/rotation. Code scanning analyzes code weaknesses but not every architectural risk. Reviews/rules protect changes but depend on meaningful reviewers and tests. Security advisories enable private remediation but require a responsible disclosure policy so researchers know where to go.

For exam scenarios, identify the problem first: secret leakage, vulnerable dependency, vulnerable source code, unsafe branch changes, ownership/review, or private vulnerability disclosure. Then select the feature designed for that stage of the secure-development lifecycle.

## m11-u06

A secure repository combines **people, process, and automation**: trained contributors, a published vulnerability-reporting path, dependency/code/secret detection, controlled pull-request integration, clear ownership, and auditable handling of exceptions. Security should be integrated early and repeated after deployment as new vulnerabilities and compliance requirements emerge.

Remember the remediation distinction: prevent sensitive files with repository/developer controls where possible; if a credential was committed, rotate/revoke it rather than assuming a later deletion makes it safe. Likewise, dismissing an alert is an accountable risk decision, not a substitute for fixing a valid vulnerability.
