# Source-audited additions — Module 12

## m12-u04

GitHub authorization is hierarchical. A user's effective access can come from direct repository assignment, one or more teams, organization defaults, or enterprise-level policy. When multiple grants apply, GitHub generally gives the user the **highest effective repository permission** granted through those paths, while organization/enterprise policy can still restrict what actions are allowed.

### Repository roles

The five standard repository roles represent progressively broader authority:

- **Read** — view/clone and participate in normal discussion without changing repository content;
- **Triage** — manage issues and pull requests without receiving code-push authority; useful for coordinators/support/project roles;
- **Write** — normal active contributor access, including pushing where branch rules allow;
- **Maintain** — manage day-to-day repository configuration/work without the most sensitive/destructive administration capabilities;
- **Admin** — full repository administration, including sensitive settings and destructive operations.

Enterprise environments can define **custom repository roles** that extend a standard base role with selected additional permissions. The security principle is least privilege: choose the lowest role that lets the person/team do its job instead of giving Admin as a convenience.

Repository access may be granted to an organization member directly, inherited through a **team**, supplied by the organization's default permission, or granted to an **outside collaborator** who is not an organization member. Direct permission can override a lower inherited level by producing the higher effective access.

### Fork administration

A fork is an independent Git repository connected to an upstream repository network. Public repositories can be forked. Organizations can place restrictions on private-repository forking, and internal-repository forks stay within their enterprise boundary. Administrators should treat fork policy as part of data-governance design, because a fork can create another repository copy with its own branch/history while remaining related to upstream.

### Repository Insights

The unit includes administration through **Insights**, not only permissions. Useful sections include contributor activity, traffic, commits/activity, code-frequency data, and the dependency graph. These views help administrators understand project health, engagement, contribution patterns, and dependency/security context. Visibility of specific insights depends on repository/plan/permission conditions.

### Access auditing

Repository Settings/Manage access provides a combined view of users and teams that can access a repository. Organization and enterprise **audit logs** provide historical evidence about membership and permission changes. REST/GraphQL APIs can also enumerate collaborators, teams, and effective permissions for continuous or large-scale auditing.

A robust access review asks: who can reach the repository, through which grant, at what role, when/why that grant changed, and whether the access is still necessary. Branch protections/required reviews add a separate control over how authorized writers actually change critical branches.

### Team roles and nested teams

A GitHub team groups organization members so repository access can be granted consistently. At the team-management level, a **Member** participates in the team while a **Maintainer** can additionally manage team metadata/membership and several team settings. Organization owners can promote team maintainers.

Teams can be nested. Members of child teams inherit relevant parent-team repository permissions, allowing access to follow organizational structure. This is useful but can also make effective access non-obvious, so audit the full inheritance path rather than only direct repository collaborators.

When a team itself is granted repository access, the same repository-role model applies: Read, Triage, Write, Maintain, or Admin. This is separate from whether someone is a team Member or team Maintainer. For example, a team Maintainer is not automatically repository Admin unless the team's repository grant provides that level.

The exam distinction to keep clear is **scope**: repository roles govern one repository; team roles govern team administration; organization roles/policies govern the organization; enterprise roles/policies govern the enterprise account and its organizations. Correct administration chooses both the right permission level and the right scope.

## m12-u07

A sound GitHub administration model combines **scope, identity, permissions, and policy** rather than solving each repository independently. Teams group members and can inherit or receive repository access; organizations establish membership, base permissions, security configuration, outside-collaborator access, and repository policy; enterprise accounts can apply broader governance across multiple organizations. The administrator should grant the lowest practical role, understand every inheritance path that contributes to effective access, and review access when responsibilities change.

Authentication controls and authorization controls solve different problems. 2FA and passkeys strengthen account sign-in; PATs, SSH keys, deploy keys, applications, and repository roles determine how people or automation access GitHub resources. SAML can federate enterprise sign-in, while SCIM and managed-user designs address identity lifecycle and provisioning in supported environments. Central policy, audit logs, named identities, and separation of duties make those decisions reviewable and reduce inconsistent one-off administration. The durable operating principle is to apply controls at the appropriate repository, organization, or enterprise scope while preserving least privilege and clear accountability.
