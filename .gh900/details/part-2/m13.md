# Source-audited additions — Module 13

## m13-u01

Identity administration separates two questions: **authentication** proves who the user is; **authorization** determines what that authenticated identity, credential, or application may access. Enterprise GitHub deployments add centralized identity-provider (IdP) controls so account lifecycle, SSO sessions, API/Git credentials, teams, and repository access can be governed consistently instead of relying only on individual account choices.

This module therefore connects strong authentication (2FA/passkeys/WebAuthn), SAML SSO, OAuth/GitHub Apps, Enterprise Managed Users, PAT/SSH authorization, SCIM provisioning, and team synchronization. The exam skill is to identify which mechanism solves identity verification, user lifecycle, application authorization, or team membership rather than treating SAML/SCIM as interchangeable acronyms.

## m13-u02

Modern GitHub authentication supports several layers. **2FA** adds a second factor to account sign-in. **Passkeys/WebAuthn** provide phishing-resistant authentication backed by a device/credential provider and can use biometric or hardware-security-key mechanisms. GitHub Mobile can participate in supported 2FA approval flows. Stronger authentication protects account login, but it does not by itself decide which repositories the authenticated account can access.

**OAuth Apps** and **GitHub Apps** are also different. OAuth Apps usually act on behalf of an authorized user through OAuth scopes. GitHub Apps use an installation model with explicitly selected permissions and repository access, and can authenticate as the app/installation; this is generally a better fit for fine-grained automation/integration design than creating a broad user token solely for a service.

**SAML SSO** connects an organization/enterprise to an IdP so access to protected enterprise resources requires the user's IdP-authenticated session. Common IdP products include Microsoft Entra ID, Okta, OneLogin, Ping-based products, AD FS, or another compatible SAML 2.0 provider, subject to GitHub support/compatibility. SAML answers the interactive SSO question; lifecycle automation is a separate concern.

**Enterprise Managed Users (EMU)** changes the account model more fundamentally. Managed accounts are provisioned and controlled by the enterprise identity system rather than being normal independently controlled personal GitHub.com accounts merely linked through SSO. Use this model when a scenario calls for enterprise-owned identity lifecycle and tight restrictions on activity outside the enterprise.

Authorization controls extend beyond browser sessions. **Fine-grained personal access tokens** can be limited to selected repositories, permissions, and expiration, giving more constrained automation/API access than an unrestricted credential. Enterprise/organization policy can require approval or restrict token/app behavior. Custom repository roles can extend a base repository role with specific extra permissions when standard Read/Triage/Write/Maintain/Admin roles do not fit the operating model.

Other enterprise controls can include mandatory 2FA, IP allow lists, restrictions/approval for OAuth applications, default organization permissions, team-based access, outside-collaborator governance, and centralized enterprise policy. Repository visibility also matters: **public** is internet-visible, **private** is limited to explicitly authorized users, while **internal** is an enterprise visibility level intended for enterprise members rather than the public internet.

## m13-u04

After SAML authentication, users and tools still need **authorization** for Git/API access. A PAT, SSH key, or OAuth authorization can require explicit SAML authorization before it may access an SSO-protected organization. This distinction explains why "the user can sign in" does not automatically mean an existing token/SSH key is permitted to access organization resources.

**SCIM (System for Cross-domain Identity Management)** complements SAML by automating identity lifecycle operations. With supported provisioning, IdP changes can create/provision users, update identity attributes/groups, and deprovision access when people leave. SAML SSO by itself does not perform full automatic user deprovisioning, so combining authentication with lifecycle automation reduces stale access.

Where SAML and SCIM represent the same identity, identifiers must stay consistent—commonly SAML `NameID` and the SCIM `userName`/provider mapping. When identities are initially linked, GitHub associates IdP identity information with organization/enterprise membership so later lifecycle actions can be audited and managed.

Organizations using supported IdPs can configure native/paved-path provisioning integrations. The pinned curriculum names providers such as Microsoft Entra ID, Okta, OneLogin/Ping-family products and Google Workspace in relevant contexts. A custom IdP can integrate through compatible SAML and, where supported, GitHub's SCIM API.

SCIM 2.0 API concepts include creating, updating, and deleting user resources and managing group information. A provisioning request identifies a `userName`, human-name fields, and email information; GitHub uses that identity data to create/link the managed membership according to the applicable enterprise/organization model. Custom integrations authenticate through the credentials supported by the SCIM endpoint and should be tested before being made authoritative for production lifecycle management.

The operational difference between **SCIM and manual membership** is scale and consistency. Automated provisioning makes joiner/mover/leaver changes reflect the IdP quickly and provides a repeatable audit path; manual management depends on administrators remembering every membership, role, token, and offboarding step.

SAML-protected organizations also need credential/session auditing. Administrators can inspect/revoke SAML sessions and authorized credentials when appropriate. PATs and SSH keys used against SSO-protected organization resources must be authorized in accordance with the organization's SAML policy. The pinned curriculum also presents an organization SSO sign-up/onboarding URL pattern so new users can deliberately establish the SSO relationship.

For exam scenarios, choose **SAML** for federated sign-in/SSO, **SCIM** for automated provisioning/deprovisioning, and repository/team roles for what the provisioned user may do. They are complementary layers, not substitutes.

## m13-u05

**Team synchronization** maps an IdP group to a GitHub team so group membership changes are reflected in team membership. It is useful when repository permissions are granted to teams and the IdP should remain the source of truth for who belongs to those teams. Common scenarios include onboarding, department/team transfers, and removing people from access groups when they leave.

Team sync must be distinguished from user provisioning. In the classic organization model, synchronizing a group to a team generally assumes the person already has the required organization/account membership; the sync manages **team membership**, not the entire GitHub account lifecycle. By contrast, SCIM is designed for provisioning/update/deprovisioning of identities/groups. The pinned curriculum summarizes this as **Team Sync = team-level mapping**, **Group/SCIM = broader lifecycle automation**.

Supported identity/provider configuration differs by deployment/model, but Microsoft Entra ID and Okta are central examples in the curriculum. Configuration requires the organization's SSO/identity integration and a mapping between GitHub teams and IdP groups. When the mapped IdP group adds or removes a person, GitHub updates the team accordingly. Disabling synchronization stops the mapping and can remove memberships that existed because of the synchronized group, so disabling should be treated as an access change rather than a harmless toggle.

In an **Enterprise Managed Users** model, enterprise-managed identities and group provisioning provide stronger centralized lifecycle control. Managed users are constrained by enterprise boundaries; for example, their external collaboration/forking behavior is more restricted than ordinary personal GitHub.com accounts. IdP groups can be used to drive organization/team membership so authorization follows centralized identity governance.

The curriculum also contrasts team synchronization with SCIM-style user/group management in server/enterprise contexts. The durable concept is deployment-independent: **team sync controls membership of an existing GitHub team from an IdP group; SCIM controls identity/group lifecycle at broader scope**. Do not infer that mapping one team automatically creates every required account/membership in every deployment model.

The pinned lesson provides scale limits for the team-sync scenario: up to **5,000 members per team**, **10,000 members per organization**, and **1,500 teams per organization** in that curriculum snapshot. Treat numeric platform limits as source-versioned values that should be checked in current GitHub Docs when designing a real enterprise.

Terminology note: **GitHub Enterprise Server (GHES)** is the self-hosted GitHub Enterprise product. **GHE.com** refers to GitHub Enterprise Cloud with data residency, not an on-premises GHES appliance. Where older/training wording blurs those labels, use the current product distinction while retaining the identity concepts being taught.

## m13-u07

A complete GitHub identity model follows the user through the whole access lifecycle. **Authentication** proves the identity, using controls such as 2FA, passkeys, or enterprise SAML SSO; **authorization** then limits what that identity, token, SSH key, or application may do. Repository roles, teams, organization policy, fine-grained PAT permissions, application permissions, IP restrictions, and SSO authorization can all contribute to the final access decision, so successful sign-in must never be treated as proof that every repository or credential is authorized.

Lifecycle automation is a separate layer. **SCIM** can provision, update, suspend, and deprovision identities in supported enterprise configurations, while **team synchronization** maps IdP groups to GitHub teams so repository access follows managed group membership. Enterprise Managed Users goes further by placing enterprise identities under centralized lifecycle control. For integrations, GitHub Apps provide an installation- and permission-oriented model that is often preferable to shared human credentials, while OAuth Apps principally operate through user authorization. Effective administration combines these mechanisms so joiners receive only required access, movers inherit the correct team/role changes, and leavers are reliably deprovisioned instead of leaving stale credentials or memberships behind. Regular access audits verify that the intended identity, authorization, and lifecycle controls still match reality.
