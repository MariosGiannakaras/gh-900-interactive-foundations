# Source-audited additions — Module 14

## m14-u05

A pull request is the collaboration boundary for proposing repository changes, not merely a button that performs a merge. A complete PR workflow includes a focused branch, commits that represent the proposed change, a title/body explaining intent and context, review discussion, requested reviewers or Code Owners where appropriate, status checks, and an explicit merge/close decision.

You should be able to distinguish **draft** PRs from ready-for-review PRs, understand that pushing more commits updates the same PR, connect PRs to Issues so work is traceable, and interpret review outcomes such as approval, comments, or requested changes. Required reviewers/checks/rules can turn review and automation into enforced merge conditions rather than optional convention.

Finally, merge strategy affects repository history. Merge commits preserve the branch topology, squash merging condenses the PR's changes into one commit, and rebase-style merging reapplies commits onto the target history. Select the repository's approved strategy based on desired history and policy rather than assuming all merges are equivalent.
