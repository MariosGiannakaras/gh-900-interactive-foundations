# Module 15 — Search and organize repository history: Interactive submission

Read `modules/15-search-organize-history/README.md` first. Work on branch `lab/module-15`.

## Hands-on activities

1. Use repository search/filtering to find an Issue, Pull Request, commit, and file by meaningful terms.
2. Use commit history and `git log` to identify when a chosen line/file changed. Record a real commit SHA that exists in this repository.
3. Use GitHub blame on a text file and follow a commit from the blame view.
4. Create an annotated or lightweight practice tag locally, then push that tag to this learner repository so the validator can verify it. Do not create a release unless you want to.
5. Link related work using Issue/PR references or commit links so history is easier to navigate.
6. Practice qualifiers/filters for Issues and Pull Requests such as state, author, label, assignee, review status, or date as applicable.

## Knowledge check

### Q1
What is GitHub's blame view useful for?
- [ ] A. Changing repository billing.
- [ ] B. Deleting all earlier commits.
- [ ] C. Showing line-by-line attribution/history context for a file and linking lines to commits.

### Q2
Why use search qualifiers and filters?
- [ ] A. They encrypt search results.
- [ ] B. They narrow large sets of Issues, PRs, code, or other repository data to relevant results.
- [ ] C. They create branches automatically.

### Q3
What is a Git tag typically used for?
- [ ] A. Naming a specific point in repository history, commonly for versions/releases.
- [ ] B. Replacing a user account.
- [ ] C. Configuring SAML SSO.

### Q4
How does a branch differ from a tag conceptually?
- [ ] A. Tags always contain more files than branches.
- [ ] B. Branches cannot point to commits.
- [ ] C. A branch normally moves as new commits are added; a tag normally names a fixed historical point unless deliberately changed.

### Q5
Why link Issues, Pull Requests, and commits?
- [ ] A. To disable notifications.
- [ ] B. To create traceability between discussion, intent, review, and implementation history.
- [ ] C. To bypass permissions.

### Q6
What is a good way to investigate why a behavior changed?
- [ ] A. Combine search, file history/blame, commit diffs/messages, and related PR/Issue context.
- [ ] B. Delete `.git` and start again.
- [ ] C. Look only at the newest file and ignore history.
