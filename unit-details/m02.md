# Source-audited additions — Module 2

These additions preserve details from the pinned Microsoft Learn source that were too compressed in the base lesson. They are presented to learners as part of the corresponding live unit step.

## m02-u04

GitHub Issues can enter a workflow from more places than the repository **Issues** tab. Besides creating a normal issue directly, work can originate from an item in a task list, a note in a Project, a comment in an issue or pull request, a selected line of code, or a URL/query-driven workflow. This matters because an issue is the durable work record even when the need for that work is discovered somewhere else.

When creating an issue, repositories can offer **issue templates** or structured **issue forms**. Templates provide a reusable starting structure; forms can require specific fields so maintainers receive consistent information. Maintainers can then add assignees, labels, milestones, and Projects metadata. Labels, `@mentions`, and reactions are lightweight ways to classify work, bring people into the conversation, and acknowledge information without creating unnecessary comments.

GitHub **Discussions** are for broader community conversation rather than work that is already concrete enough to track as an issue. Repository owners and people with suitable write access can enable Discussions. Discussion visibility follows the repository's visibility. When Discussions are first enabled, maintainers can configure a welcome post and categories that make the intended type of conversation clear.

Default category patterns include **Announcements**, **General**, **Ideas**, **Polls**, **Q&A**, and **Show and tell**. Categories can have different formats: an announcement, an open-ended discussion, a poll, or a question-and-answer thread. In a Q&A category, an appropriate response can be marked as the accepted answer. Important discussions can be pinned. If a discussion develops into concrete work, GitHub can reference it in a new issue so the actionable task has its own trackable lifecycle while preserving the conversational context.

A useful decision rule is therefore: use an **Issue** when somebody should be able to assign, plan, implement, and eventually close a unit of work; use a **Discussion** when the primary objective is to ask, explore, announce, collect opinions, or build community consensus. A discussion can later become an issue when that conversation produces actionable work.

## m02-u08

At the end of this module, you should be able to connect the platform features into one collaboration model rather than remember them as isolated menu items. A repository provides the Git-backed project boundary; branches and commits hold changes; pull requests provide a reviewable integration proposal; Issues track actionable work; Discussions support open-ended community conversation; and notifications/subscriptions let a user follow the subset of activity that matters to them.

You should also be able to choose lighter-weight publishing surfaces appropriately: Gists for small Git-backed snippets or notes, Wikis for extended repository documentation, and GitHub Pages for a static site. The core exam skill is not merely naming a feature, but selecting the feature whose lifecycle and access model fit the scenario.
