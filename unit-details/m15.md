# Source-audited additions — Module 15

## m15-u01

Repository history is useful only if contributors can recover context from it. GitHub therefore combines Git history with search, metadata, links, blame, milestones, labels, assignees, templates, and reusable replies. These features answer different questions: "where is the code?", "who changed this line?", "what work is related?", "who owns the next action?", and "which release/goal does this belong to?"

A new contributor investigating an unfamiliar bug should use repository history as evidence rather than guessing: search for the feature name, inspect related issues/PRs/commits, use blame to find the changes/people associated with a line, and follow cross-links to the discussion that explains why the current implementation exists.

## m15-u02

GitHub exposes both **global search** and context-specific repository searches. Global search can search across repositories and result types—code, issues/pull requests, users, Marketplace and other supported categories—using GitHub search syntax. A context search on a tab such as **Issues** or **Pull requests** is already scoped to that repository/object type and exposes type-specific filters such as author, label, project, assignee, and state.

Search qualifiers can be composed. Examples from the curriculum include:

- `is:open is:issue assignee:@me` — open issues assigned to the current user;
- `is:closed is:pr author:contoso` — closed PRs authored by a named account;
- `is:pr sidebar in:comments` — PRs whose comments mention a term;
- `is:open is:issue label:bug -linked:pr` — open bug issues without a linked PR.

Qualifiers are provider/type specific. A qualifier such as `is:pr` is meaningful to issue/PR search but is not necessarily interpreted by a code-search provider. Use the search surface/qualifiers appropriate to the object you need rather than assuming one filter applies everywhere.

### Milestones, labels, and assignees

A **milestone** groups issues and pull requests around a shared target such as a release, sprint, or phase. Milestones have a title/description and can have a due date. GitHub tracks completion progress based on the state of items in the milestone. Issues/PRs can be assigned to a milestone from their sidebar, and Project views can expose milestone information as another planning dimension.

Search can filter by milestone, e.g. `is:open is:pr milestone:"Release v1.0"`. Labels provide orthogonal classification such as bug, priority, area, workflow state, or team. Combine qualifiers—e.g. `is:pr label:"ready for review" author:@me`—to narrow a large repository's history. Assignees communicate responsibility and are searchable through `assignee:`.

### `git blame` and GitHub Blame

`git blame` attributes each line in a file to the commit that last changed it, making it useful for finding the relevant historical change and likely subject-matter experts. GitHub's **Blame** view presents this information in the web UI and links commits/history for navigation. "Blame" is not a judgment mechanism; some systems even alias the same idea as "praise." Use it to recover history and context, not to assign fault.

### Cross-linking history

GitHub automatically connects some objects—for example commits/branches that make up a PR—and users can explicitly connect others. Writing `#8` can autolink a local issue/PR. Pasting a commit SHA (GitHub recognizes an adequate prefix) can link the commit. Links between issues, PRs, Projects, and commits create a navigable explanation of how a requirement became code.

An `@mention` links a person/team into the conversation and normally notifies them when permissions/notification rules allow. This is useful for requesting context from somebody associated with historical work, but should be used intentionally.

### Saved replies vs issue templates

**Saved replies** are prewritten responses that a user can insert into issue/PR comments. They reduce repetitive typing and keep common maintainer guidance consistent. They are configured in the user's settings and can be edited before posting.

**Issue templates/forms** solve a different problem: they structure the information a contributor supplies **when opening** an issue. Use a template/form to collect required reproduction steps, environment, expected behavior, or other structured fields up front; use a saved reply for recurring responses after a conversation exists.

Taken together, search, metadata, blame, and cross-links turn repository history into an onboarding/debugging resource rather than a raw list of commits.

## m15-u05

After this module, you should be able to reconstruct project context efficiently: start with global or scoped search, refine results with qualifiers, use labels/milestones/assignees to understand planning state, use Blame/commits to understand code history, and follow autolinks between issues, pull requests, and commits.

You should also choose organizational tools correctly: milestones for shared goals/releases, labels for flexible classification, assignees for responsibility, issue templates/forms for consistent intake, and saved replies for repeatable maintainer responses. These features complement Git history; none of them replaces commits/branches as the source-code history itself.
