# Source-audited additions — Module 7

## m07-u02

Modern **GitHub Projects** is substantially different from **Projects (Classic)**. The current Projects experience is a flexible data model rather than a fixed board of columns/cards.

The pinned curriculum contrasts them across four areas:

- **Layouts:** modern Projects supports table, board, list/timeline-style views where available; Classic centered on boards.
- **Data:** modern Projects can sort, rank, filter, and group items using custom fields. Supported field concepts include text, number, date, iteration, and single-select values. Classic primarily used columns and cards.
- **Insights:** modern Projects can build charts from current Project data and, for eligible plans, historical data. Classic offered much more limited progress visualization.
- **Automation/extensibility:** modern Projects exposes the ProjectsV2 GraphQL API, GitHub App scopes, webhooks, built-in workflows, and GitHub Actions integration. Classic automation focused largely on moving cards between preset columns.

Modern Projects can also show linked pull requests/reviewers, support draft issues, flexible iteration ranges/breaks, tokenized filters with saved views, customizable board cards, real-time updates, and user-presence indicators. The point of these features is to let several views represent the **same underlying work items** instead of duplicating separate boards for each perspective.

## m07-u03

A Project can be owned by an organization or by a user. The pinned exercise demonstrates an organization-owned Project: open the organization, choose **Projects**, create a new Project from a template or from scratch, and select an initial layout such as a table. Personal Projects can be created from the user's Projects area. Creating from a repository can link that repository automatically, while the Project remains its own planning object and can later relate to other repositories.

Project settings include a **name**, a short description, and a Project **README**. The README should explain why the Project exists, its scope, conventions, and what team members should understand before editing it; it is not the same as a repository README.

Issues and pull requests can enter a Project several ways:

- paste the URL of an existing issue/PR into a new Project item;
- type `#` and search a repository for matching issues or pull requests;
- bulk-add selected issues/PRs from a repository;
- use a workflow that automatically adds matching items.

Projects can also contain draft items that are not yet repository issues. Once work needs full issue behavior, convert/create the durable issue and keep Project metadata attached to the tracked work.

Built-in workflows can react when an item enters the Project and set fields such as `Status: Todo`. This is different from a GitHub Actions workflow: built-in Project workflows are configured in the Project UI for standard Project events/actions, whereas Actions or the GraphQL API are appropriate when custom automation must coordinate repositories or external logic.

The pinned Microsoft content also notes **sub-issues**: checklist work can be converted into linked issues so child work has its own metadata/status while remaining related to the parent. This supersedes older task-list-block patterns that were deprecated. Sub-issues are useful when a checklist item becomes substantial enough to require independent ownership and tracking.

## m07-u04

Custom fields let a Project model information that does not belong in a repository issue's title/body. To build a priority model, create a new field, choose **Single select**, and define values such as Urgent/High/Medium/Low. Once items are assigned values, a view can **group by** Priority. Grouped board/table views can support drag-and-drop changes, and a configured perspective can be saved as a view so the team returns to the same filter/group/layout later.

An **iteration field** represents repeated time boxes such as sprints, project phases, or planning cycles. Configure a start date and iteration duration (days/weeks), then assign items to an iteration. Iterations are data fields, not milestones: an iteration is especially useful for recurring time-boxed planning, whereas a milestone groups issues/PRs around a target goal/release and has its own repository-level progress model.

Changing the **layout** creates another perspective on the same Project data. A Board layout is useful for status/priority columns and drag-and-drop movement. A Table layout emphasizes fields and sorting. Timeline-oriented views help with date/iteration planning. Views should be saved/renamed when the perspective is meant to be shared and reused.

Built-in workflows can complement these views. For example, `Item added to project` can initialize the Status field to `Todo`. The automation changes metadata; it does not create a separate copy of the issue or PR.

## m07-u05

Project visibility and Project access are separate concepts. A Project can be **public** (viewable on the internet) or **private** (only people with appropriate access can see it). Access then controls what permitted collaborators can do.

For an **organization-owned Project**, the pinned lesson describes organization-wide base access choices such as no access, read, write, or admin, with organization owners retaining administrative capability. Project admins can additionally grant access to teams, individual organization members, and outside collaborators. For a **user-owned Project**, collaborators can receive read, write, or admin-style Project roles.

Project collaborators are managed from Project **Settings → Manage access**. A team can also be linked to a Project so it appears on the team's Projects page. Linking a Project to a repository makes a relevant Project discoverable from that repository, but the repository and Project must have compatible ownership and a repository user still needs permission to view the Project.

When work is finished, **close** and **delete** are deliberately different. Closing hides/removes an active Project from normal working lists while preserving its content and allowing it to be reopened. Deleting permanently removes the Project together with saved views, custom-field values, insights data, and draft items. Closing is therefore the safer archival operation; deletion is for data that is intentionally no longer needed.

The sub-issue model also affects Project organization. A checklist item can be converted into a dedicated linked sub-issue, allowing it to carry normal issue metadata and Project fields. Use this when nested work needs independent tracking rather than remaining only prose/checklist state in its parent.

## m07-u06

**Project Insights** builds charts from items and fields in a Project. A **current chart** shows the present state—for example, items by assignee, iteration, status, or label. Filters can narrow the source set before charting. A chart can then configure layout, axes, and optional grouping.

**Historical charts** show change over time and are plan-dependent; the pinned curriculum associates them with eligible Team/Enterprise Cloud organization Projects. A default burn-up style view can show item-status changes across time, which helps identify trend/progress rather than only today's counts.

Modern Projects can create chart types such as bar/column/line/stacked-area views and, where supported, aggregate values with functions such as count, sum, average, minimum, or maximum. Saved charts can be shared with people who already have permission to view the Project.

There are three automation layers to distinguish:

1. **Built-in Project workflows** — easiest for standard lifecycle rules such as setting Status when an item is added, reopened, closed, when review is approved/changes requested, or when a PR merges.
2. **GitHub Actions** — repository/event-driven custom automation can label/comment/manage work and use APIs/actions to add or update Project items.
3. **GraphQL ProjectsV2 API** — programmatic Project/item/field management for custom tools and integrations.

Choose the simplest layer that expresses the rule. A built-in workflow is preferable for a standard field transition; Actions is appropriate when repository events or custom logic are central; GraphQL is the foundation for bespoke Project integrations at API level.
